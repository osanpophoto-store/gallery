# おさんぽフォト ギャラリーシステム 構築記録

## システム概要

パスワード認証付きの写真販売ギャラリー。保護者がイベントごとのパスワードでログインし、写真を閲覧→枚数選択→Stripe決済→自動メール送信（写真添付 or ダウンロードリンク）の流れで完結する。

## Google Drive構成

```
Google Drive/
└── osanpophoto/
    └── イベント名/
        ├── thumbs/      → F列に設定（サムネイル用・個人Gmailと共有必須）
        │   ├── IMG-001.jpg
        │   ├── IMG-002.jpg

```

### ファイル名のルール

- **`IMG-001.jpg` 形式（3桁ゼロパディング）で統一すること**
- thumbs・original ともに `IMG-001.jpg` から始まる連番にすること
- Lightroomの書き出し設定: カスタム名 `IMG-` + 連番（開始番号を必ず1に設定）
- 透かしはLightroom書き出し時に処理する（サイトでは透かし処理なし）

⚠️ **複数クラスを別イベントとして登録する場合、originalのファイル名がLightroom通し番号のままだとthumbsの番号と一致しない。必ずLightroomで書き出し開始番号を1に設定するか、ターミナルで一括リネームすること。**

#### ターミナルでの一括リネーム手順

```bash
# originalフォルダに移動（FinderからターミナルにD&Dでパス入力）
cd /path/to/original

# IMG-001.jpg からの連番にリネーム
i=1; for f in $(ls *.jpg | sort -V); do mv "$f" $(printf "IMG-%03d.jpg" $i); i=$((i+1)); done

# 確認
ls *.jpg | head -5
```

### 共有設定

thumbs / original フォルダの両方を個人Gmailアカウント（taiki.kurono@gmail.com）と**編集者**で共有すること。

⚠️ thumbsだけ共有してoriginalを忘れるケースに注意。両方必須。

## Stripe設定

### Webhook

- エンドポイントURL: GASのデプロイURL
- リッスン対象: `checkout.session.completed`
- ※ GASがPOSTのリダイレクトを返すためWebhookは必ず失敗するが、`checkNewPayments` ポーリングで補完するため問題なし
- **StripeからWebhookエラーのメールが届いても無視してOK。エンドポイントは削除してしまっても構わない。**

### 動的PaymentLink

GASがStripe APIで都度PaymentLinkを生成。metadataに以下を埋め込む：

| キー | 内容 |
|---|---|
| `eventId` | イベントID |
| `photoNumbers` | 選択した写真の連番（`001`,`002`... カンマ区切り） |
| `isAll` | 全データかどうか |
| `qty` | 枚数 |
| `customerEmail` | 保護者のメールアドレス |

### 冪等性チェック（二重処理防止）

`checkNewPayments` は処理前にpurchase_logのA列（Stripe決済ID）を確認し、記録済みのIDはスキップする。また `created[gte]` で前回チェック以降の決済のみ取得する。

#### LAST_CHECKのリセット方法（テスト時に使用）

テストを繰り返すと `LAST_CHECK` が現在時刻に近づき過去の決済を拾えなくなる。以下を実行してリセットする：

```javascript
function resetLastCheck() {
  const oneHourAgo = Math.floor(Date.now() / 1000) - 3600;
  PropertiesService.getScriptProperties().setProperty('LAST_CHECK', String(oneHourAgo));
  Logger.log('LAST_CHECK をリセットしました: ' + oneHourAgo);
}
```

## 既知の制限・注意事項

- Google DriveのサムネイルURL（`thumbnail?id=...`）はCORSの制約でCanvas描画不可のため透かし処理はLightroom書き出し時に行う
- メール送信元は `order@osanpophoto-store.com`（個人GmailにSMTP登録済み）
- StripeのWebhookはGASで直接受信できないため1分ポーリングで代替（最大1分の遅延）
- GASの無料枠: 1日の実行時間6分、メール送信100通/日
- イベントIDにスペース・カンマを含めると照合に失敗する（必ずハイフン区切りで命名）

## 2026/07/29 水遊びイベント公開後「Stripeから入金通知が来ない」問い合わせの調査

水遊びイベント販売開始後、「入金があった場合にStripeから通知が来るようにしてあるはずだが、通知が来ない」との相談があり、Stripe MCP（`stripe_api_read`等）とGmail検索で直接調査した。

### 調査結果

- **決済自体は正常**: Stripe側で確認したところ、7/29だけで既に3件の決済が成立（¥780・¥900・¥500）。水遊びイベントの売上は問題なく入ってきている
- **写真お届けも正常**: Gmailで確認したところ、7/28 3:53の決済成立から1分後（3:54）に`order@osanpophoto-store.com`から購入者宛の写真添付メールが自動送信された記録があった。README記載の「GASが1分おきにStripeをポーリングして注文処理する」仕組み（`checkNewPayments`）が正常に動作していることを確認できた
- **「通知が来ない」の原因**: 以前設定していたStripe Webhook（GAS URL宛、`we_1TObHfF6UULduc0CgCuYsriO`）が、Stripe側で **`status: disabled`**（無効化済み）になっていた。GASがWebhookに200 OKではなくリダイレクトを返す仕様のため配信が失敗し続け、数日間の失敗を経てStripe側が自動的にこのエンドポイントを無効化したと考えられる。エンドポイントが無効化されると、それに伴う失敗通知メールも届かなくなるため、これが「通知が来なくなった」と感じられた直接の原因とみられる
- ただしこのWebhookは元々実際の注文処理（写真お届け・ログ記録）には使われておらず、無効化されていること自体に実害はない（README「Stripe設定」セクションに記載済みの想定内挙動）

### 補足: 通知設定のPush/メールの仕組み

上記の続きで、「取引と残高」タブの「成功した支払い」行でPushにはチェックが入っているがメールは未チェック、という状態を確認した。StripeのPush通知はStripe Dashboardモバイルアプリ（iOS/Android）にログインしている場合のみ届く仕組みで、ブラウザやOS通知とは無関係。アプリ未インストールだと何も届かないため、「メール」列にもチェックを入れるよう案内した。

## 2026/07/29 カート永続化機能（家族に見せてから購入できるように）

「カートに入れたまま記憶させたい。一回入れたものを家族に見せてから購入できるように。今はページを閉じたら全てリセットされてしまう」という要望を受けて実装。

### 仕組み

- `localStorage` に、選択中の写真番号一覧をイベントIDごとのキー（`osanpo_cart_<eventId>`）で保存する
- 写真を選ぶ・外す・お気に入りから一括カート追加する・カートをクリアする、いずれの操作でも保存し直す（`saveCartToStorage()`）
- ギャラリーに入る際（ログイン時・セッション復元時の両方）、保存されていればカートを復元する（`loadCartFromStorage()`）。写真グリッドの選択枠・チェックマーク表示、カートバーの枚数・金額表示も復元時に再現される
- 購入完了後（`?paid=1`で戻ってきたタイミング、および「トップに戻る」ボタン）は、そのイベントのカート保存を消す（`clearCartStorage()`）。購入済みの写真がカートに残り続けることはない
- お気に入り（❤️）は今回の対象外。従来通りページを離れるとリセットされる（必要であれば同じ仕組みで対応可能）

### 制約（ユーザーに伝達済み）

`localStorage`は「その端末・そのブラウザ」にのみ保存される。例えば保護者がスマホでカートに入れても、別の家族の別端末には引き継がれない。同じ端末・同じブラウザでタブを閉じて後で開き直すケースに対応するもの。複数端末間で共有したい場合は別途サーバー側の保存が必要になる（今回のスコープ外）。

### 動作確認方法（ユーザーによるテスト手順）

1. 実際のイベントのギャラリーにログインし、何枚か写真をカートに追加する
2. タブまたはブラウザを閉じる（ログアウトはしない）
3. 同じURLに再度アクセスし、同じパスワードでログインする → カートに入れた写真がそのまま選択された状態で表示されればOK
4. 購入まで完了させた場合は、再度同じイベントにログインしてカートが空になっていることを確認する

#### 顔認識機能について（2026/07/28 検討メモ）

保護者が自分の子供の写真だけ絞り込めるようにする機能。技術的には実現可能だが、今の構成からは一段規模が大きくなる。

- Google Cloud Vision APIは顔検出（位置・表情等）はできるが、本人特定（顔認識）は倫理的配慮から非対応。顔認識にはAWS Rekognition（顔類似検索、1000枚あたり数十〜百円程度と低コスト）か、Azure Face API（顔識別機能はLimited Access指定でMicrosoftの審査・承認が必要、個人運営の規模では現実的でない）などの外部サービスが必要
- 現状のGAS（Apps Script）だけでは重い画像処理ができないため、Cloud Functions等で外部APIを呼び出す層を新規に追加する必要がある。写真アップロード時に顔データを抽出→保護者が基準となる自分の子供の写真をアップロード→類似度で絞り込み表示、という流れになる
- 対象が未就学児の顔（生体情報）のため、個人情報保護法上の要配慮個人情報に近い扱いになりうる。保護者への説明・同意取得、データの保管・削除ポリシーの整備が必要
- やるなら小さく1イベントで試すのがよさそう


#### 写真カテゴリ分け販売について（2026/08/17 検討メモ）

集合写真・グループ写真（友達と一緒）・スナップ写真（自分の子がメイン）に分けて売る案。第3優先（将来）の検討候補として追加。今年度（2026年度）は実験年としてイベント単位の売上・利益データを集めることに専念し、実装は次年度（2027年度）以降の候補として保留。

**背景**

フジフイルムのスクールフォトはL版単体だと利益が薄く（1枚あたり利益約90円）、集合写真（980円・学校へのロイヤリティ込み）の販売が利益の大半を占める構造になっている。おさんぽフォトはデータ納品で印刷コストがなく限界費用がほぼゼロなので、特定商品に利益を集中させる必要はない。ただしカテゴリごとに購買動機が違う（集合写真＝記念で全員が欲しい、グループ写真＝一番欲しがられる、スナップ＝良ければ買う）ため、カテゴリ別に価格設計を変える余地はある。

**カテゴリ定義（「これはスナップでしょ」と揉めないための機械的な基準）**

- 集合写真: 撮影者が意図的に整列・ポーズさせて撮る、クラス全体（またはその大半）の記念撮影
- グループ写真: 撮影者が指示していない自然な流れの中で、ピントが合っていて顔がはっきり判別できる子どもが2人以上写っている構図（クラス全員ではなく一部＝友達同士）
- スナップ写真: 上記の条件を満たす子どもが1人だけの構図（他の子が写り込んでいても背景・ボケ・端切れなど脇役扱い）
- 2人だけの「ペア写真」をグループ扱いにするかどうかは未確定。実際に運用に入る際にtaikiさんの感覚で下限人数を決める

**技術的な実現可否**

- 現状、写真にカテゴリ情報は一切ない（ファイル名はIMG-001.jpg等の連番のみで、スプレッドシート・Driveどちらにもタグ用の項目がない）
- 手動タグ付け方式（Lightroom書き出し時に番号ごとに分類し、スプレッドシート等に持たせてギャラリー側でフィルタ表示）であれば、既存コードの延長で実装可能。増えるのは編集時の分類作業のみで、技術的なハードルは低い
- 顔認識で「うちの子が写っているか」を自動判定する方式（上記「顔認識機能について」参照）は個人特定を伴い、外部API・Cloud Functions層の追加、未就学児の生体情報についての同意取得等が必要で大掛かりになる。今回の「写真の種類」による分類はこの重い自動化を必要としない
- カテゴリ別に価格を変える場合は料金計算ロジック（Code.gs側）の改修が必要。Code.gsは未共有のため、実装するタイミングで共有してもらう
